# Resume library and master resume (idea, not built yet)

> Replaced by [STAGE-4A-CAREER-LIBRARY.md](STAGE-4A-CAREER-LIBRARY.md), which turns this idea into a plan. Kept for history.

Written down so it can be picked up later. The current priority is attaching a resume to a cold email (see
[STAGE-7B-OUTREACH.md](STAGE-7B-OUTREACH.md)). Nothing in this file is built except where marked **Built**.

## What the user wants

### 1. A "Resumes" page that shows every resume in readable form

- Every resume that enters the app is listed in one place: the base resume uploaded with the profile, resumes
  uploaded while attaching to a cold email, and past resumes imported from the Profile page.
- Each one can be read as **Markdown** (headings, bullets), next to the original file (open or download).
- The Markdown comes from the file itself, **without AI**. Use libraries and rules:
  - DOCX: `mammoth` can convert to HTML or Markdown directly and keeps headings, lists and bold.
  - PDF: `unpdf` gives text per page; headings and bullets have to be recovered with rules (line size, bullet
    characters, blank lines). This is the harder half. Scanned PDFs have no text and stay unsupported.
  - Store the result next to the file so it is computed once, not on every view.
- Every one of these resumes is also **embedded** (split into sections, vectors in pgvector) so that writing a resume,
  cover letter or email later can pull the user's real past wording for a given job.

### 2. A master resume (optional)

- One combined resume with **no length limit**: everything the user has done, merged from all their resumes.
- Why: the same job gets described differently depending on the target role. Example: the current position may be
  worded as developer relations in one resume, software engineering in another and product management in a third. The
  master resume keeps all of those angles, so the writer can choose the wording that fits the job.
- AI generated by merging the library, **always reviewable and editable**, never silently overwritten (same rule as
  profile fields marked "user" in company research).
- Completely optional: generation must work without it, from the profile and the retrieved sections alone.
- Shown on the Resumes page, with the date it was last built and which resumes went into it.

## Rough design

- **Resumes page** (`/resumes`): a list (name, where it came from, date, index state) and a reader pane with a Markdown
  view, a "Original file" link and an "Index status" badge. Source labels: Base resume, Uploaded for a job (links to the
  job), Past resume.
- **Tables**: add `markdown text` (and `markdown_method`: `mammoth` or `pdf-rules`) to `resume_indexes`, since that table is
  already keyed by file. The master resume is a small versioned table of its own (id, markdown, built_from file ids,
  created_at; every rebuild is a new row, like `profile_versions`).
- **Building the master**: one model call over the Markdown of all resumes, instructed to keep every distinct fact and
  every distinct phrasing of the same role, deduplicate exact repeats and invent nothing. Review screen shows the result
  and a diff against the previous master before saving.
- **Using it later**: when generating, retrieval searches the chunks of all resumes (and the master, if present) with
  the job description as the query. `searchResumeChunks()` already does this part.

## What exists already

- **Built**: stored files for every resume (`files`, content-addressed, never changed), extracted text for past resumes,
  and the index pipeline (extract, structure, split into sections, embed, store in `resume_chunks`, search with
  `searchResumeChunks`). See `src/lib/resume/`.
- **Built**: Profile page lists past resumes and the base resume.
- **Not built**: the Resumes page, Markdown conversion, the master resume.

## Open questions

- The index pipeline currently asks the model to structure each resume (to split it by job and project). That is a
  separate step from the no-AI Markdown conversion above. Once Markdown exists, sections can be split from its headings
  instead, which drops the model call from indexing. Decide when the Markdown conversion is built.
- How to treat two resumes with the same job worded differently when building the master: keep both wordings (the
  current intent) or ask the user to pick.
- Whether the master is embedded too, or only the source resumes are.
